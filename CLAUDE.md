# Vortaq

Independent, open-source desktop database client (macOS first, also Windows/Linux; MySQL today) that can import Navicat data (connections, batch jobs, `.nb3` backups). Spanish UI, English code and comments. Formerly called **ElectronDB** and, before that, **Navidog**; the GitHub repository and the repo folder still use the old names.

## Commands

- `npm run dev` — Electron + Vite dev mode
- `npm run check` — lint + typecheck + unit tests (must pass before finishing any task)
- `npm test` / `npm run test:watch` — Vitest (projects: `node`, `web`)
- `npm run test:integration:required` — the gate: MySQL and backup suites against MySQL 8.4 (`VORTAQ_TEST_MYSQL_URL=mysql://root:navidog@127.0.0.1:33306/navidog_test`) and 5.7 (`VORTAQ_TEST_MYSQL57_URL=mysql://root:navidog@127.0.0.1:33357/navidog_test`); a missing URL fails the run. Servers: `docker compose -f tests/docker-compose.yml up -d --wait`. Version-specific expectations are marked `5.7 split` in the tests; add one only for a real server difference, never to loosen an assertion.
- `npm run test:integration` — same suites, but a server without its URL is skipped. The macOS keychain test also needs `VORTAQ_TEST_KEYCHAIN_DIR=<scratch dir>`: it creates a throwaway keychain there and deletes it.
- `npm run build` — production bundle to `out/`; `npm run dist` — installers in `release/`
- Smoke test after a build: `VORTAQ_USER_DATA=<tmp dir> VORTAQ_SMOKE=1 VORTAQ_PLAIN_SECRETS=1 npx electron .` (exit 0 = renderer loaded, IPC answered). Always use `VORTAQ_USER_DATA` for manual runs so the real profile and LaunchAgents are untouched.

## Layout

- `src/shared/` — domain types (`types.ts`), the typed IPC contract (`ipc.ts`), engine descriptors and capability flags (`engines.ts`; only `mysql` has a driver, other engines are preview-only, see `docs/multi-engine-design.md`) connection validation shared by main and the dialog (`connectionValidation.ts`) and the SQL dialects (`dialects/`: splitting, both production-guard classifiers and quoting; `mysql.ts` holds the v0.1.0 functions moved verbatim and pinned by `dialects/golden/mysql.json`, whose outputs must never be regenerated from the code under test; the old paths `main/mysql/sqlSplit.ts`, `shared/sqlSplit.ts`, `shared/productionGuard.ts`, `renderer/.../query/writeGuard.ts` and `renderer/.../utils/sql.ts` re-export them for one phase). **The IPC map is the only API between renderer and main.** Add a channel there first, then implement `src/main/ipc/<area>.ts`, then use it from the renderer through `window.vortaq.invoke`.
- `src/main/` — Electron main. Modules: `db/` (engine-neutral layer: `driver.ts` interfaces, `registry.ts` engine → driver with lazy imports, `manager.ts` ConnectionManager with open dedupe/secrets/SSH tunnel/fatal/closeAll and the MySQL-only `getSessionFactory` for backups and jobs, `errors.ts` `DbUserError`/`ServerError`/`describeForLog`/capability gates, `tunnel.ts`, and the generic `query.ts`/`tableData.ts`/`rowChanges.ts` loops), `navicat/` (import), `mysql/` (the MySQL driver: `driver.ts` adapts the mysql2 pool to `db/driver.ts`; introspection, queries, row changes and their SQL; `manager.ts` and `tunnel.ts` are re-export shims for one phase), `backup/` (.nb3 read/write/restore), `automation/` (jobs, scheduler, launchd), `credentials/`, `storage/` (JSON repos in userData), `migration/` (one-time ElectronDB/Navidog -> Vortaq profile and secret migration), `updates/` (checks GitHub Releases for a newer version: notify only, never downloads or installs; network calls stay in main via `net.fetch`; `app:openExternal` only allows `https://github.com/Y0rshB3/ElectronDB/releases/...`: the repository keeps its old name for now), `ai/` (bring-your-own-key AI assistant: Anthropic adapter on the official `@anthropic-ai/sdk`, every other provider on the official `openai` SDK; provider calls go through Electron `net.fetch` from main only, keys live in `CredentialStore` kind `ai` and are never returned to the renderer). **AI privacy rule:** only database structure may reach a provider. The context builder reads metadata exclusively through `MetadataQueryable` (`ai/metadata.ts`), which refuses anything but `SELECT … FROM information_schema.*` / `SELECT VERSION()`; never send row values, query results, cell contents, connection hosts, users, passwords or names. The only other statement the assistant may issue is `EXPLAIN` of a single SELECT on user action (`ai/explain.ts`). The assistant never executes SQL: generated SQL is only inserted into the editor.
- `src/preload/` — contextBridge only, no logic.
- `src/renderer/` — Vue 3 + Vuetify 3 + Pinia. Views under `src/views`, reusable components under `src/components`, stores under `src/stores`, `src/api.ts` wraps `window.vortaq`. `src/engines/` is the engine UI registry: `mysql.ts` points at today's designer/DDL/user-SQL/editor modules (views reach them through `useEngineUi`), `capabilities.ts` (`can`, `groupsFor`, `descriptorOf`) drives menus, toolbar, tree groups and the backup/job pickers. Read neutral metadata (`typeKind`, `primary`, `kind`, …) through `utils/columnMeta.ts`, which falls back to the MySQL checks. Tree node ids are `:`-joined percent-encoded segments: build them only with `nodeIds`. MySQL menus and toolbar are pinned by `__tests__/__snapshots__/mysqlMenus.test.ts.snap`; never regenerate it to make a change pass.
- `tests/fixtures/navicat/` — anonymised Navicat files + a synthetic `.nb3`. Never add real hosts, users or data.
- `docs/navicat-storage.md` — verified Navicat formats. Read it before touching import/backup code.

## Naming and the legacy names (ElectronDB, Navidog)

- Product name and identifiers live in `src/main/brand.ts` (`APP_NAME`, `LEGACY_APPS` newest first, `UPDATE_REPO`); env switches are read with `envVar()` (`src/main/env.ts`): `VORTAQ_<NAME>`, with `ELECTRONDB_<NAME>` and `NAVIDOG_<NAME>` accepted as undocumented fallbacks.
- Keep the old names only where they identify legacy data or a stable identifier: `src/main/migration/`, `LEGACY_APPS` (profile folders, "ElectronDB Safe Storage" / "Navidog Safe Storage" keychain items, `dev.y0rshb3.electrondb.job.*` / `dev.y0rshb3.navidog.job.*` launchd labels), the env fallbacks, the `appId` `dev.y0rshb3.electrondb` (Windows installer GUID and macOS bundle id: never change it, see `electron-builder.yml`), the GitHub repo `Y0rshB3/ElectronDB` (`UPDATE_REPO`, `publish`), the localStorage keys `electrondb.*` (saved queries, column widths...; `navidog.queries.*` is adopted once), the backup source value `'electrondb'`, the test compose project `electrondb-test`, and the throwaway test MySQL credentials (`root`/`navidog`, db `navidog_test`).
- CSS tokens and utility classes keep the internal `--nd-*` / `nd-` prefix on purpose (it stands for the oldest name); do not rename them.
- Migration runs once per profile: `runProfileMigration` before app `ready` copies the newest legacy profile (`<appData>/ElectronDB`, else `<appData>/Navidog`) into `<appData>/Vortaq`, never overwriting and never deleting, and writes `migrated-from-<name>.json` (`*.json`, `logs/`, `Local Storage`, `ai/`; on Windows also `Local State`; never `backups/`, which stays in use where it is). `runSecretMigration` runs right after the context: it re-encrypts `credentials.json` (passwords and AI keys); on macOS it reads the old safeStorage keys with `security`, ElectronDB's first and Navidog's only for values the newer key cannot decrypt. Old launchd agents of jobs present in the new profile are replaced by `dev.y0rshb3.vortaq.job.*` ones. A one-time info notice says the data moved. A scratch profile (`VORTAQ_USER_DATA`) skips it.
- Test-only switches, never for real use: `VORTAQ_NAVICAT_CANDIDATES=<dirs>` replaces the automatic Navicat folder search (screenshots/tests); `VORTAQ_LEGACY_USER_DATA=<dir>` migrates from that folder even into a scratch profile (its folder name, `ElectronDB` or `Navidog`, says which product wrote it); `VORTAQ_LEGACY_KEYCHAIN=<file>` reads the legacy "… Safe Storage" items from that keychain file instead of the login keychain.

## Conventions

- Tests live next to code as `*.test.ts`; node-side tests must not import `electron`.
- Never log query data, passwords or backup contents. Secrets go through `CredentialStore` only.
- Any operation that writes to a connection whose environment requires typed confirmation (`requiresTypedConfirm` in `src/shared/typedConfirm.ts`: always `production`, plus the environments listed in `AppSettings.typedConfirmEnvironments`) must require explicit confirmation: the UI dialog (`useConfirm().confirmDestructive`) and then `confirmProduction: true` in the IPC call (`WriteOptions`). Main enforces it in `src/main/ipc/productionGuard.ts`.
- Errors thrown from IPC handlers surface to the user as their `message`: write actionable messages.
